# Verifier contract agreement — implementation evidence

5 November 2026. Implemented only `src/blocks/verify.ts`, `tests/blocks-verify.test.ts` and the three verifier exports in public `src/blocks/index.ts`. Coordinator owns contract, SPICE hash emission, integration and project handoff. No native builds, mechanical work, paid calls or production changes ran here.

Public signatures are executable from the root index:

- `REQUIREMENT_METRICS`: closed eight-entry registry matching the agent's agreed metric/argument/operator names.
- `evaluateRequirements(requirements, facts): GateResult`: validates the data-only requirement schema, compares supported facts, and returns explicit per-requirement `pass`, `fail` or `unsupported`.
- `factsFromPlan(plan, blocks, spice?): DeviceFacts`: accepts validated electrical plan facts, with conservative upstream current accounting and actual SPICE provenance checks. The initial task annotation of GateResult for this function was confirmed a typo by coordinator; the return type is DeviceFacts.

A failure makes `GateResult.ok=false`. Unsupported remains a warning/result status and **never satisfies completion**; as agreed in the coordinator report, `ok` alone only means no failed assertion, so completion must require every confirmed result's status to be `pass`. Requirements are not modified or loosened.

Battery runtime is an explicitly estimated, ideal same-rail capacity/typical-current calculation. A positive `args.capacity_mah` overrides design capacity; zero or omitted override uses `batteryMah`. Missing capacity, zero/NaN/infinite or inverted current facts, and overflowing numeric estimates return unsupported. With a named hypothetical capacity but no known battery path, measured hypothetical hours and `estimated=true` remain visible while status is unsupported. Capacity is never inferred from charger ratings, part names or generic capacity guesses. A plan can identify a battery path only through a declared battery-class external root source and actual electrical load graph; a charger alone does not prove battery-backed operation. No plan capacity or cost is fabricated.

Board `[width,height]` constraints compare coordinatewise for both `within` and `<=`; `[60,40]` is valid and never sorted or implicitly rotated. Scalar voltage intervals require ordered low/high. Malformed operators, targets, units, arguments, unknown metrics/fields and duplicate IDs fail. Missing facts do not pass. Pin capability checks require a unique named mapping with nonempty valid capability strings. Plan aliases derive from actual MCU facts, roles, linked nets and protocols after ERC; reserved/fixed-function pins are not presented as general application GPIO. Aliases normalize naming without assuming ESP32 numeric GPIOs. Ambiguous mappings are withheld.

Current facts aggregate every declared direct sink once, then propagate downstream demand through the actual source graph. Linear conversion preserves current; switching conversion uses conservative output-high/input-low voltage and declared efficiency. Charger programming demand is included. Only one external supply/current domain is reported; multiple roots, missing loads/conversion facts or invalid electrical graphs leave load facts unsupported. Example tested graph: 120 mA typical/250 mA peak at 3.3 V through a 5 V, 80%-efficient converter, plus 10/20 mA input overhead, yields **109/226.25 mA at the single 5 V root**, not the sum at every stage. A linear variant yields 130/270 mA. These declared estimates are not hardware measurements and omit any real-world consumption absent from the reviewed budgets.

Interfaces derive deterministically from block class/id, bus protocols and USB-C sink constraints. Planned board dimensions and part counts are populated only for an electrically valid graph. Part count includes every declared instance's components. Complete prices and battery capacity are absent because the current block contract does not provide verified values.

`netVolts` never copies nominal ERC source voltages. Only actual passing SPICE divider-output measurements with V units, an audit evidence reference and **matching `inputHash===schematicHash(plan,blocks)`** become measured facts on the real shared divider net. Instance-qualified aliases always remain scoped; a bare net name is used only when globally unambiguous. RC crossing time and ideal charger-law outputs are not rail-voltage evidence. Stale plan/content identity, absent provenance or failing SPICE gates leave voltage unsupported. Direct `evaluateRequirements` can consume explicit carrier `DeviceFacts.netVolts/netVoltEvidence` without expecting a block-plan hash; caller owns the authenticity of those supplied facts.

The coordinator's electrical identity hashes declared block content hashes, which the library resolver validates. Direct raw BlockDef callers must preserve that validated-content boundary; a forged unchanged contentHash must not be used to relabel edited component data. This was explicitly reported to coordinator for integration review.

Validation: **9/9 pure tests pass**, no failures/skips, latest reported total **407.37 ms** before the final targeted typecheck. Cases cover hypothetical/known battery paths, capacity override/fallback, inverse constraints, unknown facts, zero/nonfinite/overflow inputs, malformed schemas/units/operators, dimensional semantics, generic MCU aliases, conservative no-double-count power propagation and no invented cost/voltage.
